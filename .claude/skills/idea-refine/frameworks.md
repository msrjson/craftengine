# Ideation Frameworks Reference

Use these frameworks selectively. Pick the lens that fits the idea at hand; never run
every framework mechanically. The goal is to unlock thinking, not to complete a
checklist.

## SCAMPER

A structured way to transform an existing idea through seven operations:

- **Substitute:** which component, material or process could be swapped? What if the
  core technology changed? The target audience? The business model?
- **Combine:** what if this merged with another product, service or idea? Which two
  things that rarely go together would create something new?
- **Adapt:** what else is like this? Which ideas from other industries, domains or
  eras could be borrowed? Is there a parallel in nature?
- **Modify (magnify or minimize):** what if it were ten times bigger? Ten times
  smaller? What if one feature were exaggerated, or everything stripped to the bare
  minimum?
- **Put to other uses:** who else could use this? Which other problems could it solve?
  What happens in a completely different context?
- **Eliminate:** what happens if a feature disappears entirely? What is the
  zero-configuration version? What does it look like with half the steps?
- **Reverse or rearrange:** what if the steps ran in the opposite order? What if the
  user did the work instead of the system, or the reverse? What if the value chain were
  flipped?

**Best for:** improving or reimagining existing products and features. Less useful for
greenfield ideas.

## How Might We (HMW)

Reframe problems as opportunities with the "How might we..." form:

- Start from an observation or a pain point
- Reframe it as "How might we <desired outcome> for <specific user> without <key
  constraint>?"
- Write several framings of the same problem; different framings unlock different
  solutions

**Qualities of a good HMW:**

- Narrow enough to act on ("...help new users find relevant content in their first
  five minutes")
- Broad enough to leave room for creative solutions (not "...add a recommendation
  sidebar")
- Holds a tension or constraint that forces creativity

**Qualities of a bad HMW:**

- Too broad: "How might we make users happy?"
- Too narrow: "How might we add a button to the settings page?"
- Solution-embedded: "How might we build a chatbot for support?"

**Best for:** reframing stuck thinking. When someone is anchored on a solution, pull
them back to the problem.

## First Principles Thinking

Break the idea down to its fundamental truths, then rebuild from them:

1. **What do we know is true?** Not assumed, not conventional: actually true.
2. **What are we assuming?** List every assumption, including the ones that feel
   obvious.
3. **Which assumptions can be challenged?** For each, ask whether it is a law of
   physics or just how it has been done so far.
4. **Rebuild from the truths.** With only the fundamental truths in hand, what would
   you build?

**Best for:** escaping incremental thinking, when every idea feels like a small
improvement on the status quo.

## Jobs to Be Done (JTBD)

Focus on what the user is trying to accomplish, not on what they say they want:

- **Functional job:** which task are they trying to complete?
- **Emotional job:** how do they want to feel?
- **Social job:** how do they want to be perceived?

Form: "When I <situation>, I want to <motivation>, so I can <expected outcome>."

**Key insight:** people do not buy products; they hire them to do a job. The real
competitor is often outside the category. A video streaming service competes with
sleep, not only with other streaming services.

**Best for:** understanding the real problem, when you are not sure the right thing is
being solved.

## Constraint-Based Ideation

Impose constraints on purpose to force creative solutions:

- **Time:** what if you had one day to build it?
- **Features:** what if it could have only one feature?
- **Technology:** what if the obvious technology were off the table? (In a Craft
  application: what if it needed no new table? No new plugin? No JavaScript at all?)
- **Cost:** what if it had to be free forever?
- **Audience:** what if the user had never used a computer?
- **Scale:** what if it had to serve a billion users? What about ten?

**Best for:** cutting through complexity, when the idea keeps growing or stays vague.

## Pre-mortem

Imagine the idea has already failed, then work backwards:

1. It is twelve months from now. The project shipped and flopped. What went wrong?
2. List every plausible cause: technical, market, team, timing, compliance.
3. For each failure mode: is it preventable? Is it a signal the idea must change?
4. Which failure modes are acceptable? Which would kill the project?

**Best for:** Phase 2 evaluation, stress-testing ideas that feel good but have not been
pressure-tested.

## Analogous Inspiration

Look at how other domains solved a similar problem:

- Which industry has already solved a version of this?
- What would this look like if a company famous for a specific strength built it?
- Which natural system works this way?
- Which historical precedent exists?

Look for *structural* similarity, not surface similarity. "The ride-hailing app for X"
is surface-level. "A two-sided marketplace that solves a trust problem between
strangers" is structural.

**Best for:** Phase 1 expansion, generating variations that feel genuinely different
from the obvious approach.
