# Release report: Craft Engine 4.4 and the CRM demo

- **Period:** 2026-10-05 to 2026-10-06
- **Versions:** 4.4.0 r00022 (published, tag on `166741d`); 4.4.1 r00023 (cut
  locally, held by the owner until released)
- **Decision record:** `docs/adr/0004-extension-model.md`
- **Guides:** `data/documentation/extensions.md`, `data/documentation/plugins.md`

## Summary

The framework now grows through isolated extensions instead of through its own
code. A complete CRM built only from extensions, installed from the published
release like any third-party project, surfaced eight framework defects that the
framework's own suite could not see. All eight are fixed in 4.4.1, each with a
regression test that failed before its fix, and a demo rehearsal is now a
mandatory step of every release.

## What 4.4 changes

An application adds extensions: modules (business features and screens),
plugins (capabilities several modules use) and themes (presentation only). The
engine is the runtime; each extension is a unit it runs.

- Each extension is a directory with an `extension.toml`, routes, views,
  migrations, translations in `en`, `pt-BR` and `es`, and assets.
- Install, activate, deactivate and uninstall without a restart, from the CLI
  or a management panel. Uninstalling never deletes data.
- Fault isolation per extension: one that fails at load is left out; one that
  fails repeatedly is taken out of service by its circuit breaker (its routes
  answer 503) while the rest keeps serving. Typed domain errors never count.
- A module never imports another one: the boundary gate refuses
  `EXTENSION_CROSS_IMPORT` at build time. Modules talk through the internal
  proxy, events and filters.
- Generators for agents: `make module`, `make plugin`, `make theme`,
  `make screen` write extensions that install and run as they are.
- `data/` stays slim: the framework ships no application code. The bundled
  `audit-log` example moved to the demo.

## The CRM demo

Repository `msrjson/craftengine-demo` (local directory `data-demo/`, container
`craftengine-demo` on port 9002 with its own PostgreSQL on 5500). It installs
the engine from the GitHub release tag and never from the framework sources.

| Extension | Kind | Proves |
|---|---|---|
| `companies`, `contacts`, `deals`, `activities` | modules | modules that depend on each other and talk only through the proxy; a screen degrades instead of failing when another module is out of service |
| `deals` -> `activities` | modules | a won deal emits `crm.deal.won`; another module schedules exactly one follow-up without knowing the emitter; money as cents plus ISO 4217 |
| `dashboard` | module | each module adds its own card and menu entry through filters; a deactivated module disappears from both |
| `extension_manager` | module | the management panel is itself an extension: if it fails, the CRM keeps serving and the CLI stays the way back in |
| `audit_log` | plugin | an audit trail of identifiers only, no names or emails (LGPD/GDPR) |
| `harbor` | theme | a light and dark theme overriding the layout by path |

The demo suite has 28 tests: 13 integration tests and a 15-step HTTP
walkthrough (register, admin role, every screen, the sales flow, a refused panel
action, a module switched off and on).

## Framework defects the demo found

None was visible to the framework's suite, which runs inside the repository.

| Defect | Why the framework suite missed it | Fix (4.4.1) |
|---|---|---|
| The published package lacked the login and layout templates | the files exist in a source checkout | templates added to `package-data`; `tests/test_package_data.py` fails on any data file left out or hidden |
| An extension added while the server ran never started serving | tests created extensions before boot | `reconcile()` rediscovers manifests on every pass |
| `make auth` / `make admin` left half a scaffold behind on failure, which blocked every rerun | templates never went missing in the repository | both check every template and destination before writing the first file |
| `make admin` told you to assign an `admin` role it never created | the onboarding test created the role by hand | a generated forward-only migration seeds the role |
| `regex:` split its pattern on commas, so `[.,]` raised a 500 | no test used a comma in a pattern | the pattern of `regex` / `not_regex` is taken whole |
| **Security:** `redirect.back()` followed any `Referer` (open redirect) | no test checked the origin | only a relative path or the request's own host is followed |
| Two routes on the same path: the winner depended on load order | no auth route collided with a module before | activation refuses `EXTENSION_ROUTE_CONFLICT`; at boot the application route wins and the clash is logged |
| CSRF refusals rendered hardcoded English | the language gate does not cover that part of the engine | typed 419 `CSRF_TOKEN_MISMATCH` and 403 `CSRF_ORIGIN_REJECTED` with keys in three locales |

## Process obstacles

- **Publishing was blocked by the session's permission controls.** The
  release push and the creation of the public demo repository were done by
  another agent from the instructions on the team board.
- **Half-written scaffold files were committed in the demo.** The 4.4.0
  `make admin` crash left them behind; removing them took three passes until
  the generator's full output list was compared with the demo's files.
- **A session restart wiped the temporary rehearsal.** It became durable: the
  walkthrough is a demo test, and the rehearsal is
  `.claude/scripts/rehearse-demo.sh`.
- **A concurrent commit touched the append-only team board.** The board was
  rebuilt from its committed version plus the new lines, losing nothing.
- **An own mistake:** a test sent a relative `Referer`, which no browser
  sends; investigating the resulting 403 exposed the hardcoded CSRF copy.

## Why the framework is easier to maintain

| Before | Now |
|---|---|
| Growing the application meant changing central code | Growing it means adding a directory; the engine is untouched |
| Modules could import each other unnoticed | The build refuses cross-extension imports |
| One failing module could take the application down | Its circuit breaker takes only that extension out of service |
| Turning a plugin off needed a restart | Deactivation undoes every contribution at once, in every worker |
| Packaging defects surfaced after a release | The demo rehearsal runs before every release, on SQLite and PostgreSQL |
| Framework, site and demo shared one context | Three contexts, each with its own repository, container and port |
| Decisions lived in conversations | ADR 0004, the extensions guide, the CHANGELOG and the release procedure |

Figures: the framework suite grew from 1784 to 1862 tests on SQLite (1924 on
PostgreSQL); the rehearsal passes 28 of 28 demo tests on each database.

Limit, stated in ADR 0004: isolation is in-process. It contains what an
extension raises, not an infinite loop or memory exhaustion. The planned path is
an out-of-process transport for the internal proxy.
